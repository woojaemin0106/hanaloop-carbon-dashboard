# 작업 소요 시간 및 AI 활용 기록

이 문서는 최종 제출을 위해 작업 시간, 시간이 많이 소요된 부분, AI 활용 방식, 사용 프롬프트, 의사결정 이유를 누적 기록합니다.

## 기록 원칙

- 작업 시간은 커밋 시각, 검증 로그, 실제 진행 내용을 기준으로 보수적으로 기록한다.
- 최종 제출 전 실제 총 작업 시간을 다시 합산해 README에 반영한다.
- AI 활용 내역은 `AI가 도운 일`과 `지원자가 판단한 일`을 분리해 기록한다.
- AI 활용 기록은 `왜 그렇게 판단했는지`, `생성 결과를 어떻게 검토했는지`를 중심으로 남긴다.

## GitHub 작업 규칙

- `main`은 배포용 브랜치, `develop`은 개발 통합 브랜치로 사용한다.
- 기능 작업은 `develop`에서 새 브랜치를 만들어 진행하고 PR 대상도 `develop`으로 둔다.
- 파일 하나를 수정한 뒤 해당 파일을 재검토하고 커밋한다.
- 마지막 파일 작업 후 전체 재검토와 수기 검토를 진행한다.
- PR 제목은 항상 `FEAT : 작업 내용` 형식으로 작성한다.
- PR 머지 후 원격 작업 브랜치를 삭제한다.
- 기능 PR 머지 후 로컬 `develop`은 원격 `develop`과 다시 동기화한 뒤 다음 작업을 시작한다.

## 시간이 많이 소요된 부분

| 항목 | 이유 | 대응 |
| --- | --- | --- |
| 과제 요구사항 파악 | 평가 기준이 도메인 이해, 시스템 설계, UX, 설명력으로 나뉘어 있어 단순 구현보다 제출 전략 정리가 먼저 필요했다. | 진행률 문서와 검토 로그를 먼저 만들고, 이후 작업을 PR 단위로 남기기로 했다. |
| 데이터 모델링 | 과제 데이터는 단순 표 형태지만 실제 탄소 관리 플랫폼처럼 활동 데이터와 배출계수를 분리해야 확장성을 설명할 수 있다. | `ActivityRecord`와 `EmissionFactor`를 분리하고, 배출계수에 `version`, `validFrom`을 포함했다. |
| Scope와 전과정 단계 매핑 | 원본 표에는 Scope가 직접 적혀 있지 않아 탄소 회계 관점의 해석이 필요했다. | 전기는 구매 전력으로 `Scope 2`, 원소재/운송은 공급망 활동으로 `Scope 3`에 매핑했다. |
| 작업 이력 관리 | 과제에서 커밋 히스토리를 필수로 요구하므로 한 번에 크게 커밋하면 설명력이 떨어진다. | 파일별 작업, 파일별 재검토, 커밋, 전체 재검토, PR 머지 흐름을 고정했다. |
| 브랜치 전략 정리 | 초기에 `main` 기준으로 진행했지만, 실제 협업 흐름에서는 배포용 `main`과 개발용 `develop`을 분리하는 편이 자연스럽다. | 기존 병합 결과를 기준으로 `develop`을 만들고 이후 feature PR의 대상 브랜치를 `develop`으로 조정했다. |
| API 응답 형태 설계 | 계산 결과를 그대로 화면에 연결하면 UI 요구가 바뀔 때 계산 로직까지 흔들릴 수 있다. | 계산 결과 위에 KPI, 기간, 출처 메타데이터를 덧붙이는 얇은 요약 서비스 계층을 만들었다. |
| 대시보드 정보 구조 | PCF 값은 총량, 단위당 배출량, Scope 비중, 월별 추이처럼 서로 다른 단위가 섞여 있어 한 화면에서 우선순위를 정해야 했다. | KPI 4개를 상단에 두고, 유형/Scope/월별/상위 활동 순서로 내려가며 읽히게 구성했다. |
| 로컬 브라우저 검증 | Windows 환경에서 분리 실행한 Next dev 서버가 바로 종료되는 문제가 있어 화면 검증 방식 조정이 필요했다. | 브라우저 검증 세션에서 Next 서버를 유지하고 데스크톱/모바일 뷰포트를 직접 확인했다. |
| README 정보 압축 | README가 길어지면 평가자가 핵심 구현과 설계 결정을 빠르게 찾기 어렵다. | 실행 방법, 주요 결과, 구조, 설계 결정, trade-off, AI 활용만 1차로 정리했다. |
| 입력 검증 메시지 | 숫자가 아닌 입력은 `NaN`으로 변환될 수 있어 라이브러리 기본 메시지가 사용자에게 노출될 위험이 있었다. | `Number.isFinite`로 먼저 걸러 한국어 오류 메시지를 고정했다. |
| 브라우저 상호작용 검증 | 한글 라벨 기반 Playwright 스크립트가 셸 인코딩 영향으로 깨졌다. | 실제 UI 검증은 안정적인 id 셀렉터와 메시지 영역 텍스트로 다시 확인했다. |
| 활동량 조정 범위 | 전체 30개 활동을 모두 편집하게 만들면 화면이 복잡해지고 제출 시간 대비 핵심 흐름이 흐려진다. | 상위 배출 활동 3개만 조정하게 해 감축 효과가 큰 항목을 먼저 검토하도록 범위를 제한했다. |
| 원문 요구사항 재정렬 | 초기 메일 이미지 기준으로 PCF 중심 구현을 먼저 했지만, Google Docs 원문은 회사/국가/Post 모델과 navigation drawer를 더 명확히 요구했다. | 기존 PCF 모듈은 유지하고 첫 화면을 회사형 배출량 대시보드로 전환했다. |
| React 18 제약 검토 | 원문은 React 18을 명시했지만 Next 14/15 + React 18 조합이 현재 Windows/Node 환경에서 빌드 오류를 냈다. | 검증 가능한 Next 16/React 19 조합을 유지하고 trade-off로 기록했다. |
| 제출용 캡처 | 개발 서버 캡처에는 Next dev indicator가 포함되어 제출 화면으로 부적합했다. | `npm run build` 후 production server에서 데스크톱, 모바일, rollback 상태를 다시 캡처했다. |
| UI 언어 결정 | 프로젝트 안내문은 영어였지만 UI 언어 제한은 없었다. | 국내 채용 과제 맥락과 사용성 설명력을 고려해 주요 화면 문구를 한국어 중심으로 바꿨다. |
| navigation drawer 동작 | 메뉴 클릭 시 본문 변화가 거의 없어 사용자가 동작을 인지하기 어려웠다. | 개요, 회사별 현황, 운영 메모가 각각 다른 본문 섹션을 렌더링하도록 분리했다. |
| 최종 제출 정리 | 개발 브랜치와 배포 브랜치, 스크린샷, 제출 메일 내용이 서로 어긋나면 마지막 확인에서 혼동이 생길 수 있다. | `develop` 내용을 `main`에 반영하고 최신 production 캡처와 제출 메일 초안을 함께 정리했다. |
| 스프레드시트 최종 대조 | 스프레드시트에는 PCF/GHG Scope와 작업 소요 시간 기록이 직접 평가 항목으로 적혀 있어 README에서 바로 확인 가능해야 했다. | PCF 시나리오 메뉴와 제출 스크린샷을 추가하고 README 본문에 작업 시간/난점을 직접 요약했다. |

| 스프레드시트 최종 대조 | 제출 안내 스프레드시트의 README/작업시간/AI 사용 기록 요구를 마지막으로 대조하는 데 활용했다. | README에 너무 AI 의존적으로 보이지 않도록 `AI 보조`와 `직접 판단`을 분리해 적는 방식을 유지했다. |
| 검토 자동화 | 빌드 명령 실행, 데이터 건수 확인, PR 본문 정리에 활용했다. | 수기 검토 항목을 문서로 남기고 PR 머지 전 빌드와 테스트 통과를 확인했다. |

## 사용 프롬프트 기록

| 시점 | 프롬프트 또는 요청 | AI 활용 결과 | 결정 이유 |
| --- | --- | --- | --- |
| 과제 확인 | `이메일이 왔어 확인해봐` | 과제 메일의 마감, 제출물, 평가 기준, 스프레드시트 내용을 정리했다. | 제출 범위와 평가 기준을 먼저 명확히 해야 구현 우선순위를 정할 수 있었다. |
| 시작 방향 결정 | `처음부터 진행해보자 뭐부터 할까?` | 기존 프로젝트 구조를 확인하고 선택지를 정리했다. | 기존 코드가 과제 도메인과 달라 새 레포에서 시작하는 편이 더 안전하다고 판단했다. |
| 레포 생성 | `깃허브부터 레포부터 만들어` | GitHub 레포 생성 상태를 확인하고 로컬 클론과 초기 프로젝트 구성을 진행했다. | 과제에서 Public GitHub와 커밋 히스토리가 필수였기 때문에 레포를 먼저 만들었다. |
| 작업 방식 확정 | `작업할때 원칙은 매파일마다 작업 종료시 재검토 - 커밋 ... pr -> 머지 순으로 진행한다` | 브랜치 기반 작업, 파일별 커밋, 전체 재검토, PR 머지 프로세스를 따랐다. | 제출 시 코드 작성 과정을 보여주기 위해 작업 단위를 명확히 남기는 것이 유리했다. |
| 데이터 모델링 | `진행해` | PCF 타입, 원본 활동 데이터, 배출계수 작성 과정에서 구조화와 검토를 보조했다. | 계산 로직보다 먼저 도메인 모델을 고정해야 API/UI 확장이 흔들리지 않는다. |
| 작업 기록 정리 | `작업소요시간 기록, 시간이 많이 소요된 부분, AI 활용 방식, 사용 프롬프트와 결정 이유를 정리` | 본 문서 작성 과정에서 누락될 수 있는 항목을 정리하는 데 활용했다. | README와 제출 문서에서 AI 사용 내역을 구체적으로 설명해야 하므로 작업 중간부터 기록하는 것이 정확하다. |
| 계산 로직 구현 | `그래 이제 다음작업으로 진행하자` | PCF 계산 함수, 집계 함수, 테스트 항목 작성 과정에서 구조화와 검토를 보조했다. | UI 구현 전에 계산 결과를 독립적으로 검증해야 이후 화면 오류와 계산 오류를 분리할 수 있다. |
| 자동 진행 요청 | `이작업 끝내고 다음 PR작업까지 진행해서 끝내 자동으로` | 현재 작업을 PR까지 완료한 뒤 다음 작업으로 이어갈 수 있도록 작업 순서를 관리한다. | 반복적인 GitHub 작업은 정해진 규칙대로 자동화하고, 설계 판단과 검토 내용은 계속 문서로 남긴다. |
| 브랜치 전략 수정 | `메인 브랜치 = 배포용 디벨롭 브랜치 = 개발용` | `develop` 브랜치를 만들고 이후 PR 기준을 `develop`으로 바꾸는 작업 순서를 정리했다. | 배포 브랜치와 개발 통합 브랜치를 분리해야 실제 협업/배포 흐름에 더 가깝다. |
