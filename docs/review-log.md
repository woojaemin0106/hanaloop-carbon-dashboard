## 2026-05-17 - PCF 원본 데이터와 배출계수 모델링

### 자동 검증

- `npm run build` 통과
- 변경 파일 통계 확인: 타입 파일 1개, 과제 데이터 파일 1개, 진행 문서 1개
- 활동 데이터 수 확인
  - 전기: 9건
  - 원소재: 12건
  - 운송: 9건
  - 총 활동 데이터: 30건
- 배출계수 수 확인: 4건

### 수기 검토

- 제품 코드는 과제 시트의 `CT-045`를 사용했다.
- 제품명은 과제 시트의 `컴퓨터 화면`과 영문 보조명 `Computer Screen`을 함께 기록했다.
- 전기 사용량은 구매 전력으로 보아 `Scope 2`에 매핑했다.
- 원소재와 운송은 공급망 활동으로 보아 `Scope 3`에 매핑했다.
- 전과정 단계는 `제조 에너지`, `원소재 조달`, `상류 운송`으로 분리했다.
- 배출계수는 활동 데이터와 별도 배열로 분리했고, `version`과 `validFrom` 필드를 두어 DB 테이블 전환과 버전 이력 추적이 가능하게 했다.
- 과제에서 생산 수량이 별도로 제공되지 않아 `productionQuantity`는 현재 과제 데이터 묶음 1개 기준으로 두었다. 이후 UI에서 사용자가 생산 수량을 조정하거나 PCF 단위 환산 기준을 명시하는 방향으로 확장한다.

### 다음 검토 포인트

- 계산 로직에서 `활동량 x 배출계수 = kgCO2e` 결과가 수기로 계산한 기준값과 일치하는지 확인한다.
- 월별, 활동 유형별, Scope별 집계 결과에 중복 월 데이터가 합산되는지 확인한다.

## 2026-05-17 - PCF 계산 로직 구현

### 자동 검증

- `npm run build` 통과
- `npm run lint` 통과
- `npm run test` 통과
  - 총 5개 테스트 통과
  - PCF 계산 테스트 4개 통과
  - 앱 진입점 smoke 테스트 1개 통과

### 수기 검산

- 전기 활동량 합계: 1,029 kWh
  - 계산식: `1,029 x 0.456 = 469.224 kgCO2e`
- 원소재 플라스틱 1 활동량 합계: 3,186 kg
  - 계산식: `3,186 x 2.3 = 7,327.8 kgCO2e`
- 원소재 플라스틱 2 활동량 합계: 106 kg
  - 계산식: `106 x 3.2 = 339.2 kgCO2e`
- 운송 활동량 합계: 839 ton-km
  - 계산식: `839 x 3.5 = 2,936.5 kgCO2e`
- 총 배출량: `469.224 + 7,327.8 + 339.2 + 2,936.5 = 11,072.724 kgCO2e`
- Scope 2 총량: `469.224 kgCO2e`
- Scope 3 총량: `10,603.5 kgCO2e`
- 2025년 5월 중복 행 합산 결과: `2,210.076 kgCO2e`

### 구현 검토

- 배출계수는 활동 유형과 라벨이 모두 일치해야 매칭되도록 했다.
- 배출계수 `validFrom`이 활동일보다 늦으면 사용할 수 없도록 했다.
- `factorVersion` 옵션을 두어 특정 버전의 배출계수로 재계산할 수 있게 했다.
- 활동량이 음수이거나 생산수량이 0 이하이면 오류를 던지도록 했다.
- 월별 집계는 같은 월의 중복 행을 합산하도록 했다.
- Playwright 기본 테스트에서 dev 서버 자동 실행을 제거했다. Windows 환경에서 Next dev 서버가 종료되지 않아 테스트 명령이 타임아웃되었고, 현 단계의 검증 대상은 계산 로직이므로 서버 의존 없는 테스트로 분리했다.
- ESLint 설정은 Next 16의 flat config export를 직접 사용하도록 수정했다. 기존 `FlatCompat` 방식은 순환 구조 오류로 `npm run lint`가 실패했다.

### 다음 검토 포인트

- 내부 API 또는 조회 계층에서 계산 결과가 그대로 노출되는지 확인한다.
- UI에서 총량, 월별, Scope별 값의 단위가 `kgCO2e`, `tCO2e`로 혼동 없이 표시되는지 확인한다.

## 2026-05-18 - PCF 요약 서비스와 내부 API 구성

### 자동 검증

- `npm run lint` 통과
- `npm run test` 통과
  - 총 7개 테스트 통과
  - 기존 PCF 계산 테스트 4개 통과
  - PCF 요약/API 응답 테스트 2개 통과
  - 앱 진입점 smoke 테스트 1개 통과
- `npm run build` 통과

### 수기 검토

- `summary-service.ts`는 계산 로직을 다시 구현하지 않고 `calculatePcf` 결과에 기간, KPI, 데이터 출처만 추가하도록 했다.
- KPI 단위는 서로 섞이지 않게 구분했다.
  - 총 배출량: `tCO2e`
  - 제품 단위 PCF: `kgCO2e/데이터 묶음`
  - Scope 3 비중: `%`
  - 최대 배출 활동: `kgCO2e`
- `/api/pcf/summary` route handler는 서비스 계층만 호출한다. 화면에서 API와 같은 응답 구조를 재사용할 수 있어 UI 컴포넌트가 계산 함수에 직접 의존하지 않는다.
- Scope 3 비중은 `10,603.5 / 11,072.724 x 100 = 95.8%`로 수기 검산했다.
- 최대 배출 활동은 기존 계산 테스트와 동일하게 `2025-04 플라스틱 1`, `1,173 kgCO2e`로 확인했다.
- 브랜치 전략은 `main=배포`, `develop=개발`로 정리했고, 이후 feature PR 대상은 `develop`으로 둔다.

- 월별 추이와 유형별 요약을 같은 단위 체계로 표시하는지 확인한다.
